J'ai maintenant une vue complète de l'API SuperOps (GraphQL) et de la structure des serveurs. Voici ma proposition détaillée, suivie du script PowerShell.

Analyse de la situation
30 serveurs Windows à patch manuel, répartis en 4 groupes existants (Gruppe 1–4), avec une contrainte critique : 15 serveurs W2012R2 ne peuvent pas cohabiter dans la même fenêtre de patch que des W2019+ (incompatibilités WU agent / WSUS classification).

Proposition d'architecture
Pourquoi ne pas utiliser les catégories SuperOps comme déclencheur
L'API SuperOps ne propose pas de mutation pour déclencher une installation de patches à la demande sur un groupe d'assets. Ce qui est disponible via l'API :

getAssetPatchDetails / getAssetPatchStatus — lecture
runScriptOnAsset — exécution de script PowerShell sur un asset
assignDeviceCategory — réassignation de device category
Le déclenchement de patches via SuperOps se fait via policy (schedulée), pas via API. La voie la plus fiable pour du patch semi-automatisé à la demande est donc : script PowerShell lancé manuellement → exécute les patches via l'API Windows Update (PSWindowsUpdate ou COM WUA) sur chaque serveur ciblé, en parallèle contrôlé, avec monitoring temps réel via l'API SuperOps (lecture du patch status).

Catégories SuperOps recommandées
Créer dans SuperOps les Device Categories suivantes (Settings > RMM > Device Categories) :

Catégorie	Contenu	OS
SV_SW-Std_ Manual-Update-G1	Gruppe 1 — W2012R2	W2012R2 (15 serveurs)
SV_SW-Std_ Manual-Update-G2	Gruppe 2 — W2012R2	W2012R2
SV_SW-Std_ Manual-Update-G3	Gruppe 3 — W2019+	W2019+ (faible impact)
SV_SW-Std_ Manual-Update-G4	Gruppe 4 — Grundstoff	W2019+ (isolé réseau)
Policy associée à chaque catégorie : Patch scan only, auto-approve: None (scan uniquement, pas d'installation automatique) — c'est le script qui déclenche.

Phase 2: Pour chaque asset → runScriptOnAsset (PSWindowsUpdate install)

Récapitulatif de la proposition
Ce que l'API SuperOps permet (et ne permet pas)
Disponible via API GraphQL :

Lecture des assets par device category / patch status
Déclenchement de scripts sur les assets (runScriptOnAsset)
Lecture du patch status (polling)
Pas disponible via API : déclencher directement une installation de patches — cela reste du côté de la policy schedulée dans SuperOps. L'approche retenue utilise donc runScriptOnAsset pour pousser le script WUA directement sur chaque serveur.

Limitations connues à ce stade
Patch status polling : SuperOps met à jour le patchStatus de l'asset après le prochain scan de l'agent (typiquement quelques minutes après la fin de l'installation). Le polling peut donc indiquer Install pending encore un moment après que l'installation soit terminée sur le serveur.
Pas de résultat par KB : le monitoring via API n'expose pas le détail par patch — pour ça, il faudrait un script de reporting supplémentaire sur chaque serveur (Get-HotFix ou WUA history) que je peux préparer si nécessaire.
W2012R2 + W2019 dans même groupe : si SuperOps venait à appliquer une policy automatique à ce groupe, le comportement pourrait différer selon l'OS. À surveiller.
Dis-moi si tu veux affiner un aspect — séparation des W2012R2 dans des catégories dédiées, ajout d'un rapport par KB, ou intégration d'un ticket SuperOps automatique à la fin du run.

Vue d'ensemble de la nouvelle architecture
Règle absolue : W2012R2 + tous les DCs → AUCUN PATCH
Double protection : pas de WSUS-Approval pour le groupe + GPO AUOptions=2 (notify only). Les deux mécanismes sont indépendants — même si l'un lâche, l'autre bloque.
